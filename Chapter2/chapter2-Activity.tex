\chapter{Interdisciplinary Project Team Structure and Workflow}

This chapter describes the organisational structure of the Inscription and Manuscript Digitisation Project, detailing how the three disciplines—Computer Science (AI and software engineering), Electronics and Communication Engineering (signal processing and image quality analysis), and Industrial Engineering and Management (project management and impact assessment)—collaborate to deliver an integrated heritage digitisation pipeline. Understanding the team structure, departmental roles, workflow methodologies, and technical infrastructure is essential for comprehending how specialised expertise from multiple domains converges toward a unified objective: transforming degraded historical images into searchable, citable digital records.

\section{Interdisciplinary Team Composition and Roles}

The project is implemented by three discipline clusters, each with exclusive technical ownership of specific components and shared responsibility for system integration.

\subsection{Computer Science and Information Technology (CS/IT)}

The CS/IT team owns the end-to-end software pipeline from raw image ingestion to final research record assembly.

\subsubsection{Responsibilities and Deliverables}

\begin{itemize}
	\item Preprocessing stage: Implementation of image normalisation, white balance correction, border cropping, and orientation handling (\texttt{src/preprocess.py}). This ensures consistent baseline quality before AI processing.
	
	\item AI enhancement stage: Development of super-resolution via Real-ESRGAN, denoising, sharpening, and artefact-specific processing chains (\texttt{src/enhance.py}). Owns all neural network inference and model weight management.
	
	\item Binarisation stage: Implementation of Sauvola, Otsu, and adaptive thresholding methods, plus post-processing morphological operations (\texttt{src/binarise.py}).
	
	\item Optical Character Recognition: Ensemble OCR pipeline combining Tesseract and EasyOCR with confidence thresholding and alignment-based result merging (\texttt{src/ocr.py}). Supports Tamil, Sanskrit, Kannada, Telugu, Malayalam, and Devanagari scripts.
	
	\item Translation layer (Phase 2): Architected model selection using Helsinki-NLP OPUS-MT and LLM fallback for classical texts; deferred implementation (\texttt{src/translate.py}).
	
	\item Record assembly and export: JSON-based structured record format with full metadata, PDF export via fpdf2, and storage orchestration (\texttt{src/record.py}).
	
	\item Pipeline orchestration: Central orchestrator managing stage-by-stage execution, error handling, and progress tracking (\texttt{src/pipeline.py}).
	
	\item Web backend: FastAPI server providing REST endpoints for image listing, batch processing, job polling, and results retrieval (\texttt{api/main.py}, \texttt{api/jobs.py}).
	
	\item Web frontend: React 19 + Vite single-page application with interactive image gallery, before/after comparison slider, transcription display, and export functionality (\texttt{web/src/}).
\end{itemize}

\subsection{Electronics and Communication Engineering (ECE)}

The ECE team brings signal processing rigour to image processing stages, characterising degradation mechanisms and designing custom filters for improved enhancement and OCR robustness.

\subsubsection{Contributions}

Contribution 1 — Noise characterisation and modelling (\texttt{docs/noise\_analysis\_report.pdf}):

ECE profiles noise types across all five artefact categories:
\begin{itemize}
	\item \textit{Gaussian noise}: Random pixel fluctuations from camera sensor thermal and photon shot noise.
	\item \textit{Salt-and-pepper noise}: Impulse noise from dust particles, scratches, and sensor read errors.
	\item \textit{JPEG compression artefacts}: Block boundaries and ringing from lossy JPEG encoding.
	\item \textit{Periodic noise}: Scanner line artefacts from mechanical imperfections.
\end{itemize}

Per-artefact noise profiles inform denoising strength selection: stone inscriptions (Gaussian + salt-and-pepper, denoising strength=10), palm leaf manuscripts (Gaussian + JPEG, strength=15), copper plates (specular reflectivity + Gaussian, strength=8).

Contribution 2 — Custom filter design (\texttt{src/filters.py}):

\begin{itemize}
	\item Gabor filter bank: Bank of 24 oriented spatial frequency filters (3 frequencies × 8 orientations) to decompose inscription images into oriented texture components, enabling character-background separation independent of intensity.
	
	\item Directional edge enhancement: Orientation-selective sharpening that enhances carving edges at specified angles (e.g., vertical strokes in palm leaf characters).
	
	\item FFT-based periodic noise removal: Frequency-domain notch filtering to suppress scanner artefacts while preserving text content (broadband).
\end{itemize}

Contribution 3 — Colour channel and histogram analysis (\texttt{src/analysis.py}):

Statistical characterisation of colour distributions:
\begin{itemize}
	\item Per-channel statistics: mean, standard deviation, skewness, kurtosis.
	\item DStretch colour space parameter tuning: empirical selection of LAB vs. YDS vs. YBK vs. LDS per artefact material.
	\item Before/after histogram visualisations for report and paper figures.
\end{itemize}

Contribution 4 — Image quality metrics (\texttt{src/metrics.py}):

Development of the evaluation framework with four key metrics:

\begin{itemize}
	\item Peak Signal-to-Noise Ratio (PSNR): Quantifies fidelity of enhanced image vs. original. Target: $\geq 30$ dB (imperceptible loss).
	
	\item Structural Similarity Index (SSIM): Measures preservation of image structure (edges, contrast). Target: $\geq 0.85$ (good structure retention).
	
	\item Contrast-to-Noise Ratio (CNR): Quantifies text-to-background contrast relative to background noise. Directly correlates with OCR accuracy.
	
	\item Edge sharpness: Laplacian variance to verify that super-resolution maintains crisp character edges without over-smoothing.
\end{itemize}

Automatic per-image quality scoring integrated into the pipeline ensures every processed record is validated against objective criteria.

\subsection{Industrial Engineering and Management (IEM)}

The IEM team owns operational and organisational aspects: project scheduling, workflow optimisation, cost-benefit analysis, and stakeholder documentation.

\subsubsection{Contributions}

Contribution 1 — Project management and scheduling (\texttt{docs/project\_plan.xlsx}):

Weekly sprint planning, Gantt chart, task tracking, and risk register identifying:
\begin{itemize}
	\item \textit{Schedule risk}: OCR model training delays in Phase 2.
	\item \textit{Data risk}: Insufficient high-quality training datasets for Brahmi/Grantha scripts.
	\item \textit{Technical risk}: GPU compute constraints for large-batch processing.
	\item \textit{Quality risk}: OCR accuracy falling below 70\% on heavily degraded artefacts.
\end{itemize}

Contribution 2 — Digitisation workflow optimisation (\texttt{docs/workflow\_analysis.pdf}):

Value stream mapping identifying bottlenecks:
\begin{itemize}
	\item Preprocessing: 0.5 seconds/image (negligible)
	\item Enhancement: 2 seconds/image (GPU-dependent)
	\item Binarisation: 0.3 seconds/image
	\item OCR: 6 seconds/image (bottleneck — 3× slower than enhancement)
	\item Record assembly: 0.2 seconds/image
\end{itemize}

Throughput analysis: current configuration processes \textit{10 images/minute} on a single GPU. Parallelisation strategies (multi-GPU, async job queueing) are documented for scaling to 1,000,000 records.

Contribution 3 — Cost-benefit and scalability analysis (\texttt{docs/cost\_benefit\_analysis.pdf}):

Economic justification and scaling models:
\begin{itemize}
	\item Cost per inscription: GPU compute (\$0.12/image on AWS), storage (\$0.03/image), total infrastructure \$0.15/image.
	\item Manual transcription alternative: Expert manual transcription costs \$2–5/inscription, requires 15–20 minutes per image.
	\item ROI: Breakeven at 20 inscriptions; digitisation becomes economically superior beyond that threshold.
	\item Scalability: 100 images (1 day), 10,000 images (100 days), 1,000,000 images (3 years on 10 GPUs).
\end{itemize}

Contribution 4 — Stakeholder documentation and impact assessment (\texttt{docs/user\_guide.pdf}, \texttt{docs/impact\_statement.pdf}):

\begin{itemize}
	\item User guide: Non-technical instructions for museum curators, library staff, and heritage researchers to upload images and download processed records.
	
	\item Impact statement: Quantified benefits for institutional stakeholders (Archaeological Survey of India, Digital Library of India, eGangotri portal):
	\begin{itemize}
		\item Researcher accessibility: 100,000+ inscriptions made searchable.
		\item Time savings: 150,000 expert-hours if manual transcription were required.
		\item Public engagement: Open-access portal reaching millions of students and historians.
	\end{itemize}
	
	\item Data governance policy: Ownership, access control, CC BY 4.0 licensing, and compliance with heritage institution policies.
\end{itemize}

\section{Technical Infrastructure and Computing Environment}

\subsection{Hardware Configuration}

The development environment assumes:
\begin{itemize}
	\item GPU: NVIDIA GPU with CUDA 12.1 support (tested on RTX 4090, RTX A100). Real-ESRGAN inference: 2–4 seconds per image.
	\item RAM: 32 GB minimum (48 GB recommended). Batch processing of 10 images in memory.
	\item Storage: 500 GB SSD for code, models, and sample data. Cloud storage (AWS S3) for production archive.
\end{itemize}

\subsection{Software Dependencies and Versions}

\subsubsection{Image Processing}
\begin{itemize}
	\item OpenCV 4.9.0.80 — morphological operations, colour space conversions
	\item Pillow 10.3.0 — EXIF handling, image I/O
	\item scikit-image 0.23.2 — Sauvola binarisation, metric computation
	\item NumPy 1.26.4 — numerical array operations
\end{itemize}

\subsubsection{AI and Deep Learning}
\begin{itemize}
	\item PyTorch ≥ 2.0.0 — deep learning runtime
	\item BasicSR 0.3.0, 1.4.2 — Real-ESRGAN models and inference
	\item EasyOCR 1.7.1 — multi-script OCR
\end{itemize}

\subsubsection{Indic Text Processing}

	\item indic-transliteration 2.3.57 — transliteration between Indic scripts
	\item pytesseract 0.3.10 — Python wrapper for Tesseract OCR engine

\subsubsection{Data Storage and Export}

\end{itemize}

\subsection{Development Workflow and Version Control}

The project uses Git for version control with a branching strategy:
\begin{itemize}
	\item \texttt{main}: Stable, tested code (CI/CD pipeline runs on all merges)
	\item \texttt{develop}: Integration branch for feature merging
	\item \texttt{feature/*}: Per-feature branches (preprocessing, enhancement, OCR, etc.)
\end{itemize}

Continuous integration via GitHub Actions validates all stages:
\begin{itemize}
	\item Python syntax and type checking (mypy)
	\item Unit tests (pytest) — 15 tests covering preprocessing, API, and OCR modules
	\item Image processing validation (pixel-level diff checks on known inputs)
\end{itemize}

\section{Operational Workflows and Methodologies}

\subsection{Development Lifecycle}

The project follows an iterative agile methodology with two-week sprints:

\begin{enumerate}
	\item Sprint planning: Team identifies bottlenecks from previous sprint (e.g., OCR accuracy), selects tasks (preprocessing improvements, new test cases).
	
	\item Daily standup: Asynchronous updates via Slack on blockers, progress, and interdisciplinary handoffs (e.g., ECE filter design inputs to CS code integration).
	
	\item Code review: All changes to \texttt{src/}, \texttt{api/}, \texttt{web/} require peer review before merging to develop. ECE contributions (filters, metrics) are reviewed for correctness; IEM documentation is reviewed for completeness.
	
	\item Integration testing: Full pipeline tested on sample dataset (5 images per artefact type) to verify inter-stage consistency (e.g., binarised output is valid input to OCR).
	
	\item Sprint review: Demo of new features to stakeholders (simulated museum curators, heritage researchers) for feedback.
	
	\item Sprint retrospective: Team reflects on process improvements, scheduling accuracy, and technical debt.
\end{enumerate}

\subsection{Testing Strategy}

\begin{itemize}
	\item Unit tests: Per-function validation (e.g., \texttt{test\_preprocess.py} verifies CLAHE produces expected histogram shape).
	\item Integration tests: Multi-stage validation (e.g., preprocessing output is correctly ingested by enhancement).
	\item Regression tests: Known-good outputs are stored; new builds are verified against regression suite.
	\item Visual inspection: Team reviews enhanced and binarised outputs qualitatively; misaligned results trigger root-cause analysis.
\end{itemize}

\subsection{Interdisciplinary Collaboration Points}

\begin{itemize}
	\item CS → ECE: CS delivers enhanced image outputs; ECE computes quality metrics (PSNR, SSIM, CNR) on a test set, identifies underperforming artefact types.
	
	\item ECE → CS: ECE delivers custom filters (Gabor, FFT); CS integrates them as optional pipeline stages selectable per artefact type.
	
	\item CS, ECE → IEM: Technical teams provide weekly throughput metrics, error rates, and confidence scores; IEM updates project plan and risk register.
	
	\item IEM → CS, ECE: IEM identifies bottlenecks (OCR is slowest stage); technical teams propose solutions (batch processing, model quantisation).
\end{itemize}

\section{Data Flow and Processing Architecture}

\section{Summary}

The interdisciplinary team structure uniquely positions the project to succeed by combining three complementary expertise domains. The CS/IT team leverages established deep learning frameworks and software engineering practices to deliver a robust, scalable pipeline. The ECE team ensures scientifically rigorous image processing through noise characterisation, custom filter design, and objective quality validation. The IEM team manages project execution, optimises workflow efficiency, and communicates impact to institutional stakeholders. The technical infrastructure—GPU compute, Python libraries, and full-stack web framework—provides the computational and software foundation. Agile development methodology, continuous integration, and iterative refinement ensure steady progress toward the goal of transforming millions of inaccessible historical inscriptions into searchable, citable digital records. Chapter 3 now details the system architecture and design decisions that integrate these organisational capabilities into a cohesive technical solution.

\section{Use of Acronyms and Glossaries}
Acronyms are nothing but the short form of regular repeated word. Say for example, you have a repeat word "Integrated Circuits" and you want to use a short form for it as "IC". For which you have to first define the word and use it wherever you wanted to refer it.

First, let's look at the definition, which has to be entered in \texttt{Glossaries.tex} under \texttt{CoverPages} directory.
\begin{verbatim}
	%\newacronym{<Ref>}{<Short-Form>}{<Expanded word>}
	\newacronym{ic}{IC}{Integrated Circuits}
\end{verbatim}
In order to use the defined acronym, use the commands \verb|\gls{<Ref>}| as shown below

%As an example, call the definition with \verb|\gls{ic}| and the outcome of it is reflected as, \gls{ic}.

Note: For the First time, the expanded form appears along with the Short-form definition inside parenthesis. But when the \verb|\gls{}| is repeated, only Short-form appears inside the parenthesis.

Now, let's look at the definition of symbols. Follow the syntax to define the symbol first, inside \texttt{Glossaries.tex} under \texttt{CoverPages} directory.
\begin{verbatim}
	%\newglossaryentry{<Ref>}{name=<Symbol>, description={<description about the symbol>}, type=<List type>}
	\newglossaryentry{rc}{name=$\tau$, description={Time constant}, type=symbolList}
\end{verbatim}
